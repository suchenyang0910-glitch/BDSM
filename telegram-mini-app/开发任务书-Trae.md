# 同频 InTune Telegram Mini App + 管理后台开发任务书（交付 Trae）

版本：MVP v1.0  
目标：构建一个基于 Telegram 的成年用户内容目录与权益交付系统。用户在 Mini App 中浏览两列视频列表；完成有效付款后，系统按单条、内容包或会员权益发放对应私密频道访问入口。运营人员通过管理后台发布内容、管理订单、用户、权益与财务数据。

## 1. 开发范围

### 1.1 用户端 Telegram Mini App

- Telegram 身份登录与服务端验签。
- 首页：后台驱动的 Banner、分类导航、推荐/精选分区与双列视频网格；视频封面固定 16:9，每项显示封面、标题、标签、时长、价格或“已解锁”状态。
- 分类/内容包筛选。
- 内容详情：封面、简介、预览、价格、包含权益、购买/查看入口。
- 我的：会员状态、已解锁内容、内容包、订单记录、客服入口。
- 支付状态页：待支付、处理中、成功、失败、退款、已到期。
- 支付成功后刷新权益；已获授权时申请后端生成的 Telegram 私密频道短期邀请链接。

### 1.2 Telegram Bot

- `/start` 欢迎语与按钮：进入内容目录、查看我的权益、社区公约、联系客服。
- 接收支付成功/订阅变更后更新权益（由后端订单服务处理，Bot 只通知）。
- 发放访问入口：仅在服务端验证权益有效后发送或打开短期邀请链接。
- 到期/退款/人工冻结后撤销对应频道访问权限。
- 管理员通知：支付异常、退款申请、内容举报、邀请失败。

### 1.3 管理后台

- 管理员登录、角色权限、操作日志。
- 视频/内容发布管理。
- 内容包与会员权益管理。
- 用户管理。
- 订单和退款管理。
- 财务报表与对账管理。
- 运营数据看板。

## 2. 关键业务规则（必须按此实现）

1. 前端绝不能自行认定“已支付”。支付成功只能由支付服务签名回调、Telegram Stars 成功事件或有审计记录的人工确认写入。
2. Telegram `initDataUnsafe` 不可信。Mini App 把 `initData` 原文传给服务端；服务端 HMAC 验签通过后，才可创建用户会话。
3. 用户最少数据原则：只存 Telegram 用户 ID、展示名、用户名（如有）、头像地址（如有）、权益和订单；不主动索取手机号。
4. 不在网页、前端配置或固定公告中写入永久频道链接。必须由后端在权限核验通过后生成短时、单次使用链接。
5. 内容发布前必须有授权与审核记录。后台需支持下架、冻结与审计。
6. 单条付费若使用“跳 Telegram 频道”交付，则该单条内容必须映射一个独立私密频道；Telegram 频道无法对不同用户隐藏同一频道内的不同帖子。内容包/会员应优先映射共享私密频道。
7. 第一版不做：积分、充值钱包、主播直播、等级体系、PK、社交私信、自动分佣。

### 2.1 已确定的 Telegram 资源

- 公开预览频道：`https://t.me/InTune_bdsm`。Mini App 首页 Banner 可直接跳转该频道；用于公开预告、样本内容和通知。
- 平台 Bot：`@InTune_bdsm_bot`。配置为 Main Mini App 入口，并承担权益提醒和私密频道邀请发放。
- 收费频道：保持私密。Trae 不得将其邀请链接或频道 ID 写入前端、种子数据、截图或代码仓库；仅通过服务端环境变量或后台配置读取。

## 3. 推荐技术栈

| 层级 | 推荐 | 要求 |
| --- | --- | --- |
| Mini App | React + Vite + TypeScript | Telegram WebApp SDK；移动端优先；双列响应式布局 |
| 管理后台 | React + TypeScript + Ant Design | 与用户端分离路由；桌面端优先 |
| 服务端 | Node.js + TypeScript + Fastify 或 NestJS | REST API、参数校验、日志、鉴权 |
| 数据库 | PostgreSQL + Prisma | 本地可用 Docker；生产环境迁移 PostgreSQL |
| 缓存/队列 | v1 可无；后续 Redis | 支付回调幂等、任务重试时再接入 |
| Bot | Telegram Bot API | 初期可 Long Polling；生产建议 Webhook |
| 文件与封面 | 仅存元数据与 Telegram/对象存储 URL | 不在数据库存视频二进制 |

## 4. 交付物

1. `mini-app/`：Telegram Mini App 源码。
2. `admin/`：管理后台源码。
3. `server/`：API、Bot、支付回调、数据库迁移源码。
4. `docker-compose.yml`：本地启动 PostgreSQL 与服务端依赖。
5. `.env.example`：不含真实密钥的环境变量示例。
6. `README.md`：本地启动、配置 Bot、创建管理员、测试支付回调说明。
7. 接口文档（OpenAPI/Swagger）与种子数据。
8. 基础测试：身份验签、订单回调幂等、权益发放/撤销、管理员权限。

## 5. 验收标准

### 用户端

- 在 Telegram 内打开 Mini App 后，服务端能识别正确 Telegram 用户 ID。
- 视频列表固定双列展示，视频封面为 16:9；Banner、分类、推荐/精选均由后台配置；加载、空状态、网络失败状态完整。
- 未购买内容显示价格与“解锁”按钮；已购买内容显示“前往观看”。
- 用户不能通过改前端字段、复制旧链接或伪造状态获得频道入口。
- “我的已解锁内容”和订单状态与后台数据一致。

### 管理后台

- 管理员可以创建、编辑、预览、上架、下架内容；建立内容包；配置价格、权益和频道映射。
- 管理员能查找用户、查看权益、人工补发/撤销权益，所有动作有日志。
- 支付回调重复发送时，订单和权益只生效一次。
- 可以按日期导出订单、退款、收入、有效会员、待处理异常。

### 安全

- Bot Token、支付密钥只存在服务端环境变量，不能出现在仓库或浏览器端。
- Mini App `initData` 服务端验签；管理员采用独立登录和 RBAC。
- 所有创建邀请链接、人工改权益、退款、下架操作记录操作者、时间、原因与前后状态。

## 6. Trae 的实施顺序

1. 建项目骨架、数据库迁移、管理员认证与 Telegram `initData` 验签。
2. 做内容、内容包、频道映射与后台 CRUD。
3. 做 Mini App 双列列表、详情、我的权益。
4. 做订单/权益状态机与支付回调的模拟器。
5. 接 Bot：欢迎语、菜单、权限发放、到期撤销。
6. 接真实支付服务前，先由后台人工标记“支付成功”做全链路验收。
7. 最后接入选定支付通道、退款流程、运营看板与导出。
